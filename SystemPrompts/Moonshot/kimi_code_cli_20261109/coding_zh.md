# 编码规范

编写与上下文代码风格匹配的代码 — 遵循项目的命名约定和结构范式，而非使用自己的默认设置。默认不添加注释：那些解释代码用途、来源或修改原因的注释在合并时会变成噪音 — 代码和其历史记录已经说明了这些。

仅在项目已存在测试时添加新测试。若无测试，除非被明确要求，否则不要创建测试、报告或脚手架文件 — 遵循工具链的默认约定和输出命名规则。

不要因为某项库或框架常见而假设其可用性。首先在项目的导入列表、清单文件或锁文件中确认其存在，并匹配项目中已使用的版本和范式。如果某项能力确实缺失，应明确说明而非静默添加依赖。

修改完成后，清理过时行为描述的评论和文档字符串，确保它们与当前代码行为一致。

- **保留所有Markdown格式**  
  - 标题层级（#）  
  - 列表（-、*、1. 等）  
  - 链接（`URL` 或 `[描述](URL)`）  
  - 粗体（**内容**）  
  - 斜体（*内容*）  
- **代码块原样保留**  
  ```python
  # 此处无需翻译代码内容
  ```
- **行内代码原样保留**  
  例如：`context_window`, `temperature`, `top-p`  
- **术语严格对照**  
  - `LLM` → 大语言模型  
  - `system prompt` → 系统提示词  
  - `prompt engineering` → 提示词工程  
  - `RLHF` → 基于人类反馈的强化学习（RLHF）  
  - `ChatGPT`, `Claude`, `Gemini` 等保留英文  
- **技术规范**  
  - `self-attention` → 自注意力  
  - `diffusion model` → 扩散模型  
  - `safety policy` → 安全策略  
  - `refusal` → 拒绝回答  
- **输出要求**  
  完全输出翻译结果，无额外解释或格式添加。
