## 实时分析工作流

GhidraSQL以受控无头模式运行，配置：
- 临时本地libghidra RPC端口
- SQL HTTP服务`127.0.0.1:8081`
- 持久化Ghidra项目
- 关闭策略`save`

记录的操作序列：
1. 遍历二进制文件，收集函数、调用图、导入项、字符串及热点函数信息
2. 通过`_start`到`__libc_start_main`回溯恢复`main`函数
3. 基于函数地址缩小反编译查询范围，通过调用/交叉引用/字符串证据推断功能职责
4. 对15个高价值函数进行重命名、原型定义、注释标记和进度标签
5. 修改前读取目标，修改后验证，调用`save_database()`
6. 查询最终实时版本及注释数量，保存后停止受控服务器
7. 以只读模式重新打开项目，验证所有恢复的函数、原型、注释和标签持久性

最终数据库达到版本316后保存。只读模式重新加载时所有15条注释均存在。重启时显示的不同版本号（3）表示持久化项目数据库的版本号，而非注释丢失。

## 恢复结构

恢复后的架构：
1. 解析选项、区域设置、环境变量、终端状态、转义字符、颜色、时间和输出布局
2. 将操作数和目录条目存入自有文件向量
3. 根据选定排序模式与方向排序向量
4. 以长格式、列格式、行格式、逗号分隔或单列格式渲染当前向量
5. 将目录提取至延迟队列
6. 遍历队列中的目录，可选递归添加子目录

关键证据包括：
- 恢复的`main`函数
- 调用图
- 内嵌的GNU帮助文本和`src/ls.c`断言字符串
- 对`gather/sort/render/traversal`函数的独立反编译分析

## 安装与运行失败

| 阶段 | 观察到的故障 | 原因 | 解决方案 |
|---|---|---|---|
| 工具链发现 | 系统路径缺失或无法使用的JDK 21、现代CMake和Gradle | 主机工具不满足安装提示 | 本地工作区安装OpenJDK 21.0.12、CMake 3.31.8和Gradle 8.14.3 |
| Java加载器 | `libjli.so: 无法打开共享对象文件` | 可移植JDK的私有库不在加载路径 | 通过`LD_LIBRARY_PATH`指定JDK的`lib`和`lib/server`目录 |
| 临时文件 | Java/原生步骤无法依赖标准`/tmp` | 运行时没有可用的常规临时目录 | 通过`TMPDIR`和`-Djava.io.tmpdir`使用工作区`.tmp`目录 |
| 依赖传输 | HTTPS依赖解析/下载失败或中断 | 环境使用受限/代理传输且Java信任未匹配 | 使用Git传输、可续传下载和本地Java信任配置 |
| 并行构建 | 组合汇编器在并发构建中收到截断输入 | 资源压力中断编译进程并留下不完整汇编流 | 仅删除失败目标输出并串行重建 |
| Ghidra启动 | `support/launch.sh`失败，因Bash进程替换需要`/dev/fd` | 运行时无法访问`/dev/fd` | 将两个进程替换循环替换为命令替换here-strings并添加空行保护 |
| 第一个受控GhidraSQL运行 | glibc在`pthread_mutex_lock`处异常终止 | 两个cpp-httplib修订配置链接到单个可执行文件：fastmcpp的`cpp_httplib`和顶层`httplib`，因不同的OpenSSL/zlib特征宏导致内联类布局不兼容 | 强制fastmcpp的FetchContent声明复用顶层cpp-httplib源代码，公开链接`fastmcpp_core`到`httplib::httplib` |
| 第一个严格源码构建 | 跳转和"控制流到达末尾"诊断变为错误 | 编译器不知道`usage()`和内存不足处理器永不返回 | 将两个辅助函数标记为`_Noreturn`; 最终严格构建无警告 |

CMake修复是上游源码变更。Ghidra启动补丁是环境特定兼容性补丁。

非致命警告：
- Ghidra FileStore警告出现于`/var/tmp/root-ghidra/fscache2`
- 未阻止项目创建、分析、保存、干净关闭或只读重启

## 恢复限制

`recovered_ls.c`是干净的行为恢复，不声称复现原版GNU实现。刻意省略需要更多类型、全局变量、区域设置和库恢复的高级GNU特性：
- 完整转义样式
- 完整`LS_COLORS`
- ACL/SELinux列
- dired偏移量
- 超链接
- 区域设置感知显示宽度
- 版本排序
- 所有选项别名

原始Ghidra伪代码保留在查询日志中以确保可审计性。恢复的源码本身不包含任何反编译残留物。
